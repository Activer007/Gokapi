## 部署与信任模型

- 单台 VPS、单个 Gokapi 进程、少量可信注册成员；管理员负责创建和管理账号，不建设公开注册、多租户 SaaS。
- 公网访问者、分享链接持有人和 File Request 上传者不可信；可信成员的账号或 Key 也可能泄漏，所以对象授权、撤销和凭据隔离仍必须存在。
- 保持单体 Go、现有页面/WASM、SQLite/Redis、本地/S3 驱动和公开 API。首选内置登录、SQLite、本地存储作为本轮参考部署；不删除或强制迁移其他配置。
- 不承诺多进程共享数据库、跨实例会话连续性、滚动升级和分布式即时撤销。启用这些部署方式需另行评审。

## 权限方案

沿用现有 Super Admin / Admin / User 三种角色、9 个 UserPermission 位、10 个 ApiPermission 位，以及现有 authorization 纯策略函数。角色负责管理身份，用户权限控制委托，Key 权限限制凭据动作；无需增加租户、组织、团队、文件 ACL、策略语言或新权限引擎，也不迁移已有角色数值。

保留五条核心不变量：

1. 管理请求通过当前账号、当前 Key 的权限交集和对象所有权/明确委托检查。普通成员默认管理自己的文件；跨所有者操作必须有已有的对应权限。
2. 替换操作同时验证目标、源文件读取权和可选删除源权限；ZIP 逐成员检查。公开分享链接是有限、可转交的读取能力，不要求下载者拥有文件。
3. 降权、删用户或撤销 Key 完成后，后续新发起请求重新读取当前授权并拒绝旧权力。允许已通过授权的传输/任务结束，不要求回滚已输出的数据或抢占长传输。会话续期不能绕过已经完成的撤销而产生后续可用管理能力；只验证、修复单进程实际交错，不建设分布式撤销协议。
4. File Request 凭据仅用于其绑定请求的上传/分片操作，不能进入管理 API 或操作另一请求的分片；公开文件、密码 Cookie、session、presign 和 Key 的权限域不能混用。后台任务必须绑定已授权的具体资源，不能由任意外部 ID 扩大范围；不要求每个内部 I/O 都重新授权。
5. 保留已完成的 CSRF、密码 Cookie、公开下载密码/到期/次数/待删检查及历史越权修复，不因简化而回退。

## 测试与完成条件

使用已有测试，按权限等价类补缺，不要求人工扩展“所有角色 × 所有入口 × 所有状态 × 所有并发交错”的笛卡尔积。保留已有自动路由遍历；用普通所有者/非所有者、授权管理员、降权/删除主体、永久/临时/撤销 Key、File Request、公开下载者覆盖关键分支。每个重要拒绝边界有负例及正常正例；危险写入负例检查文件和元数据未改变。

M2 只保留以下收尾任务：

- SEC-020/021：复核已有集中策略、替换三重边界、撤销和公开能力证据；不再重复建设权限框架。
- SEC-021：完成单进程会话续期/撤销的一个可复现请求交错及必要最小修复。保留已有私密评估；内部快照模型不能直接当作完整 HTTP 利用证明。Key 签发仅需证明后续使用仍受当前权限约束，不要求撤销与全部在途动作跨数据库线性化。
